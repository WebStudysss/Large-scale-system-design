## A. 요구사항·도메인 모델링

1. **객실 “유형(RoomType)” 단위 예약을 택한 이유는?**
- 포인트: 재고 집계 단순화, 동시성 충돌 감소, 가격·재고 관리 분리.
- 꼬리: 특정 룸(호실 지정) 요청이 많은 호텔은 어떻게 처리?
- 면접자
    
    ## 1) 결론(두괄식)
    
    **RoomType 단위 예약은 재고 집계를 단순화하고 동시성 충돌을 줄이며, 가격·프로모션·가용성 계산을 캐시/배치로 효율화하기 위해 선택했습니다.** 호실 단위는 락 경쟁·열 폭주가 커지고 운영 복잡도가 급증합니다.
    
    ---
    
    ## 2) 이론 요약
    
    - **재고 단위(Inventory Granularity)**: 재고를 얼마나 세분화하느냐에 따라 **동시성 경합 도메인**이 달라집니다. 유형 단위는 N개 객실을 한 버킷으로 묶어 **집계-차감**(aggregate-decrement) 모델이 가능하고, 호실 단위는 N개의 개별 리소스에 **개별 락/상태**가 필요합니다.
    - **읽기-쓰기 패턴**: 조회 다수/갱신 소수 환경에선 **집계 기반 카운팅**과 **캐시 어사이드**가 유리합니다. 유형 단위는 “`(hotel, room_type, date)` 재고 카운터”만 관리하면 됩니다.
    - **가격/프로모션 결합**: 가격은 보통 **타입/날짜/정책**에 걸려 있으며, **유형 레벨 사전계산/캐시**가 설계 상 자연스럽습니다.
    
    ---
    
    ## 3) 나의 생각(트레이드오프)
    
    - **장점**: (1) 재고 차감이 **단일 카운터 갱신**으로 끝나 동시성 이슈가 작음, (2) **캐시 히트율**↑, (3) **요금 엔진**이 단순해짐, (4) **오버부킹** 정책(한도/보상)도 타입 단위로 관리 쉬움.
    - **단점/보완**: 특정 고객이 “호실 뷰·층수”를 지정하고 싶을 수 있으므로, **체크인 직전 ‘호실 배정(assignment)’** 단계로 미룹니다(soft allocation → final assignment). VIP/장애인 객실 등 **속성 제약**은 RoomType을 세분화하거나 **제약 기반 배정 룰**로 보완합니다.

    - **응답 포인트**: 저는 **유형 단위 집계 모델**로 재고를 관리하고, 예약 확정 시 **낙관적 잠금+버전 체크**로 `total_reserved`를 갱신합니다. 호실 지정 요구는 **후행 배정 단계**로 처리해 충돌면적을 최소화합니다.

    ## 5) 느낀점/개선 아이디어
    
    - **핫 타입 쏠림**이 보이면 `(hotel, room_type, date)` 파티션/샤딩으로 핫스팟 완화.
    - 재고·가격 **스냅샷 캐시** TTL을 짧게 가져가고, 확정 시엔 **캐시 무효화(or write-through)** 로 최종 정합성을 끌어올립니다.
    - 호실 속성 선호도는 별도 **제약 기반 배정 엔진**으로 확장 여지.

    ## 6) 신입 기준으로 내가 현실적으로 할 수 있는 일
    
    - **스키마/인덱스**: `(hotel_id, room_type_id, date)` PK, `total_inventory/total_reserved` 컬럼, 낙관적 잠금용 `version` 컬럼 설계 및 **마이그레이션 스크립트** 작성.
    - **예약 API 멱등화**: `Idempotency-Key` 저장소(예: Redis)로 **중복 요청 방지** 구현.
    - **동시성 테스트**: 동일 타입·동일 날짜에 동시 1,000건 부하 테스트 작성 → **음수 재고 불가** 검증 및 **재시도 백오프** 적용.
    - **캐시 전략**: 조회는 **Cache-Aside**, 확정 시 **무효화/갱신** 구현.
    - **운영 가시성**: 캐시 적중률, 실패 재시도율, 데드락·버전충돌 카운터 **메트릭 대시보드** 구성.
    - **추가 목표**: 호실 배정은 초기엔 단순 랜덤/라운드로빈으로 시작, 이후 제약 조건 반영하도록 **롤링 개선**하겠습니다. 정량 퍼센트 약속보단, **문제 재현→대응책 실험→지표로 검증**하는 루프를 꾸준히 돌리겠습니다.

1. **날짜·시간대(time zone) 처리 기준과 테스트 전략은?**
- 포인트: 호텔 현지 TZ vs UTC 저장, 경계(체크인 15:00/체크아웃 11:00) 테스트.
- 꼬리: 서머타임, 윤초, 장기 예약(수주/수개월) 캘린더 쿼리 최적화?
- 면접자
    
    ## 1) 결론(두괄식)
    
    **저장은 UTC, 비즈니스 로직은 호텔 현지 타임존(예: `Asia/Seoul`) 기준으로 처리하고, 외부 노출은 ISO-8601로 일관화합니다.**
    
    구체적으로 `Instant`(UTC) + `ZoneId`를 함께 보관하고, 날짜 개념(체크인/아웃)은 `LocalDate`로, 이벤트 시각은 `ZonedDateTime`으로 계산·검증합니다. IANA TZDB와 `java.time`을 표준으로 삼아 DST(서머타임) 경계 테스트를 자동화합니다. [위키백과+3IANA+3Oracle Docs+3](https://www.iana.org/time-zones/repository/tz-link.html?utm_source=chatgpt.com)
    
    ---
    
    ## 2) 이론 요약
    
    - **IANA TZDB**: 전 세계 타임존/ DST 규칙을 표준화해 제공(정치적 변경 시 수시 갱신). 애플리케이션은 **영문 식별자**(예: `America/Los_Angeles`)로 다루어야 안전합니다. [IANA+1](https://www.iana.org/time-zones/repository/tz-link.html?utm_source=chatgpt.com)
    - **Java `java.time` 권장 모델**
        - **`Instant`**: UTC 절대 시점, DB 저장·정렬 안정.
        - **`ZoneId`/`ZonedDateTime`**: 현지 규칙 적용한 시각 계산.
        - **`LocalDate`**: “날짜” 자체(체크인/체크아웃) 표현. [Oracle Docs+1](https://docs.oracle.com/javase/tutorial/datetime/iso/datetime.html?utm_source=chatgpt.com)
    - **표기 표준**: API 직렬화는 **ISO-8601 / RFC3339**(예: `2025-09-24T15:00:00Z` 또는 `+09:00`) 사용. 파싱·정렬이 안전함. [위키백과+1](https://en.wikipedia.org/wiki/ISO_8601?utm_source=chatgpt.com)
    
    ---
    
    ## 3) 나의 생각(트레이드오프)
    
    - **UTC 저장 + 현지 계산**은 다국적 호텔/여러 지점 지원에 강함. 반면 “자정” 경계 연산이 어렵기 때문에 **체크인/체크아웃같은 ‘날짜 개념’은 `LocalDate`*로 별도 보관해야 혼동(DST 전·후 23/25시간 등)을 줄입니다. DST 스킵/중복 시각(02:00 사라짐/두 번 옴)도 `ZonedDateTime`으로 **유효성 검사**를 걸어야 합니다. [Stack Overflow](https://stackoverflow.com/questions/23237585/daylight-saving-time-change-schedule-trigger-for-a-marginal-time?utm_source=chatgpt.com)

    ## 4) 질문 의도 파악 → 답변 포인트
    
    - **의도**: “시간대가 얽힌 예약/정산에서 데이터 정합성과 사용자 경험을 어떻게 보장하나?”
    - **포인트**:
        1. DB엔 `Instant`로 저장(불변성), 비즈 규칙은 호텔의 `ZoneId`로 계산.
        2. 체크인/아웃은 `LocalDate`(날짜 경계) → **체크인시각**(예: 15:00)·**체크아웃시각**(예: 11:00)을 `ZonedDateTime`으로 파생.
        3. API는 ISO-8601(+오프셋)로 입출력. Jackson은 기본 ISO-8601을 따르며 필요 시 포맷을 명시. [Baeldung on Kotlin](https://www.baeldung.com/jackson-serialize-dates?utm_source=chatgpt.com)

        3. **CHECK는 켜둔다**: 우회 쓰기를 막는 **세이프가드**로 유지(특히 배치/운영 SQL).
    
    ---
    
    ## 5) 느낀점/개선 아이디어
    
    - **실패/재시도 표준화:** 조건부 UPDATE 실패는 **409 or 422**로 매핑, **지수 백오프+지터** 재시도 가이드. (재시도 일반 원칙은 DDIA에서도 권장) [Rocky Warren](https://www.rocky.dev/notes/books/designing-data-intensive-applications?utm_source=chatgpt.com)
    - **관측성:** “조건부 UPDATE 실패율, 데드락 수, 락 대기시간”을 대시보드로 봐서 **핫 샤드**를 식별하고 키 분산/샤딩이나 가격·쿼터 정책으로 완화.
    - **마이그레이션 주의:** MySQL < 8.0.16 혼재 환경이면 **애플리케이션 가드(원자 UPDATE)** 를 ‘필수’로 두고, 업그레이드 후 CHECK를 켠다. [MySQL 개발자 존](https://dev.mysql.com/blog-archive/mysql-8-0-16-introducing-check-constraint/?utm_source=chatgpt.com)
    
    ---
    
    ## 6) 신입 기준으로 내가 현실적으로 할 수 있는 일
    
    - **스키마**: `CHECK (total_reserved >= 0 AND total_reserved <= total_inventory)` 추가(8.0.16+), 테스트 데이터로 **위반 케이스** 검증. [MySQL 개발자 존](https://dev.mysql.com/doc/search/?d=201&p=1&q=constraint&utm_source=chatgpt.com)
    - **DAO/리포지터리**: 위 **조건부 UPDATE**를 구현하고, **영향 행수(ROW_COUNT)** 기반으로 성공/실패를 분기. 실패 시 **짧은 재시도(백오프)** 를 넣음. [MySQL 개발자 존+1](https://dev.mysql.com/doc/en/update.html?utm_source=chatgpt.com)
    - **락 전략**: 프로모션/피크 시간대 특정 `(hotel, room_type, date)`에 한해 `FOR UPDATE NOWAIT` 적용하여 **대기 없이 즉시 실패**→상위 레벨에서 다른 타입 제안. [MySQL 개발자 존](https://dev.mysql.com/doc/en/innodb-locking-reads.html?utm_source=chatgpt.com)
    - **문서화**: “CHECK는 세이프가드, 실질 동시성은 **원자 UPDATE + (선택)락**” 원칙을 팀 위키에 정리.
    - **현실 약속**: “% 개선” 대신, **실패 케이스 재현 → 조건부 UPDATE 도입 → 지표로 검증** 사이클을 빠르게 반복하겠다.
