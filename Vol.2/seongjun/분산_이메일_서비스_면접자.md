## 1) SMTP 전송 흐름과 실패 재시도

**결론**: SMTP는 스토어-앤-포워드로 전달하며, 수신 MTA가 4xx면 큐에 넣고 지수백오프로 재시도합니다.

**이론**: EHLO → MAIL FROM → RCPT TO → DATA → 2xx/4xx/5xx; 4xx는 일시 실패, 5xx는 영구 실패.

**판단**: 외부 전송 워커가 큐에서 꺼내고, 4xx 시 `1m→2m→4m…`로 재시도, `max_attempts`/`max_age`(예: 72h) 초과 시 DLQ로 보냅니다.

**의도**: 전송 신뢰성/백오프/큐 운용을 이해했는지 확인.

**개선/한계**: 4xx 폭주 시 큐 적체—도메인별 rate-limit와 회로차단기를 둡니다.

**신입 액션**: Postfix/Haraka 같은 테스트 MTA로 4xx/5xx 시나리오 통합테스트 작성.

**근거**: RFC 5321(Enhanced Status Codes, 재시도 권고), 주요 MTA 운영 가이드.

## 2) IMAP vs POP3 선택

**결론**: 동기화·다중 단말 전제면 IMAP이 표준 선택입니다.

**이론**: POP3는 다운로드/삭제 중심, IMAP은 서버 상태 동기화(폴더/라벨/플래그).

**판단**: 웹·모바일 병행 환경에서 IMAP + IDLE로 신착 알림, POP3는 호환 옵션으로 최소 지원.

**의도**: 사용자 경험/프로토콜 특성 매핑 능력.

**개선/한계**: IMAP은 상태 관리 코스트↑—서버 커넥션/메일박스 락 최적화 필요.

**신입 액션**: Dovecot + IMAP IDLE 로컬 실습, 지연/동접 측정.

**근거**: RFC 9051(IMAP4rev2), RFC 1939/2449(POP3).

## 3) 첨부가 원본보다 커지는 이유(전달 효율)

**결론**: Base64 인코딩으로 약 **33%** 오버헤드가 생깁니다.

**이론**: Base64는 3바이트→4문자; 패딩 포함 평균 4/3 배.

**판단**: 첨부는 객체저장소에 두고, 메일 본문에는 링크/메타만 저장해 큐와 인덱스를 보호합니다.

**의도**: 저장/전송 코스트 감각.

**개선/한계**: 프라이버시/링크만 유출 위험—서명된 URL과 짧은 만료 적용.

**신입 액션**: 10MB, 50MB 파일 인코딩 후 실제 바이트 차이 측정 리포트.

**근거**: RFC 2045(MIME/Base64).

## 4) SPF/DKIM/DMARC를 왜 모두 쓰나(전달성)

**결론**: 세트로 써야 **발신자 위조 방지 + 도메인 정렬**을 달성합니다.

**이론**: SPF=보낸 IP 검증, DKIM=콘텐츠 서명, DMARC=정책·정렬·리포팅.

**판단**: 트랜잭션/마케팅 도메인 분리, DMARC `p=none→quarantine→reject` 단계 전환.

**의도**: 대량 발송의 평판/검증 체계 이해.

**개선/한계**: 포워딩 시 SPF 깨짐—DKIM 보강과 ARC 고려.

**신입 액션**: 샌드 도메인에 세 프로토콜 설정 후 Gmail Postmaster로 신뢰도 추적.

**근거**: RFC 7208(SPF), RFC 6376(DKIM), RFC 7489(DMARC), Google Postmaster.

## 5) 범주 분리(트랜잭션/마케팅)와 IP 평판

**결론**: 도메인/서브도메인/IP 풀 분리로 평판을 **격리**합니다.

**이론**: ISP는 도메인·IP·콘텐츠·참여도(오픈/클릭/스팸신고)로 평판을 평가.

**판단**: `noreply@tx.example.com`(트랜잭션), `noreply@mk.example.com`(마케팅)로 분리, IP Warm-up 스케줄 적용.

**의도**: 운영 관점의 실전 판단력.

**개선/한계**: 인프라 복잡도 증가—모니터링 대시보드 통합 필요.

**신입 액션**: warm-up 러니북 작성(일 발송량, 실패/오픈율 임계치).

**근거**: 주요 ESP/ISP 가이드(구글/마이크로소프트 전달성 문서).

## 6) 수신 파이프라인과 큐·멱등성

**결론**: “SMTP LB→수신 MTA→수신 큐→스팸/AV→메타DB·객체저장소→검색 색인”에 **멱등 키**로 중복을 억제합니다.

**이론**: 분산 시스템 기본 보장은 at-least-once; 중복은 소비자 멱등처리.

**판단**: `Message-ID`+본문 해시로 멱등키 구성, DB UPSERT/색인 upsert; 실패는 DLQ로.

**의도**: 메시징 보장/데이터 일관성 감각.

**개선/한계**: 외부 시스템까지 EOS는 현실적으로 어려움—단계별 멱등·보상 트랜잭션.

**신입 액션**: Kafka 소비자에 멱등키 캐시(Redis) 추가하여 중복 처리 E2E 테스트.

**근거**: Kafka EOS/Exactly-once 개념 문서, 분산 시스템 멱등 패턴.

## 7) 메타데이터 DB vs 본문/첨부 저장소 분리

**결론**: **헤더/라벨/상태**는 RDB/키밸류, **본문/첨부**는 객체저장소가 최적입니다.

**이론**: 접근 패턴(작고 빈번 vs 크고 순차)과 내구성/비용 특성이 다름.

**판단**: RDB 파티션 키 `tenant_id + user_id`(또는 user shard), 클러스터 키 `folder + sent_at desc`; 본문은 S3, 키는 content-hash.

**의도**: 스키마/파티셔닝 능력.

**개선/한계**: RDB 핫키—유저 샤딩·time-bucket. S3 지연—프리사인URL/캐시 계층.

**신입 액션**: 1천만 행 샘플 스키마로 인덱스/페이징 성능 측정.

**근거**: AWS S3 내구성/수명주기 문서, 대규모 메일 설계 사례.

---

## 8) 검색: DB 인덱스 vs 전문검색(ES)

**결론**: 제목/보낸이/날짜는 DB 인덱스, 본문·첨부 텍스트는 ES로 **CQRS** 분리합니다.

**이론**: RDB B-Tree는 정형 쿼리 최적, ES는 역색인·토크나이저로 전문검색 최적.

**판단**: 수신 이벤트 기반 비동기 색인(배치, refresh_interval↑), 한국어는 Nori/사용자 정의 사전.

**의도**: 읽기보다 쓰기가 많은 워크로드 튜닝 사고력.

**개선/한계**: 색인 지연으로 “검색에 늦게 뜸”—UI에 “색인 중” 배지·강제 리프레시 옵션.

**신입 액션**: 동일 데이터셋으로 RDB vs ES 질의 지연 비교 리포트.

**근거**: Elasticsearch 공식 가이드(Analyzer/Indexing).

---

## 9) 실시간 알림(IMAP IDLE vs WebSocket)

**결론**: 웹메일은 WebSocket, 메일 클라이언트는 IMAP IDLE 병행이 실용적입니다.

**이론**: IMAP IDLE=서버 푸시 확장, WS=양방향 프레임.

**판단**: 수십만 동시 연결은 커넥션 게이트웨이/하트비트/백프레셔/재연결 지수백오프 설계.

**의도**: 동시성/네트워크 제약 이해.

**개선/한계**: 모바일 백그라운드 제약—푸시 중계(FCM/APNs)와 하이브리드.

**신입 액션**: WS 서버에 10만 가상 커넥션 부하 테스트(JMeter/WebSocket 플러그인).

**근거**: RFC 6455(WebSocket), RFC 2177(IMAP IDLE).

## 10) API 안정성(Idempotency-Key, 페이징)

**결론**: `POST /messages`에 Idempotency-Key로 **중복 발송 방지**, 리스트 API는 **커서기반 페이징**을 씁니다.

**이론**: 네트워크 재전송은 불가피; 서버가 멱등키로 동일 요청을 한 번만 처리.

**판단**: 응답에는 `message_id`, `status=accepted`와 재시도 safe 헤더를 포함.

**의도**: API 소비·재시도 현실 대응.

**개선/한계**: 키 저장소 일시 장애—TTL 캐시와 영속 스토리지 이중화.

**신입 액션**: 멱등키 충돌/만료/재전송 유닛·통합 테스트 작성.

**근거**: Stripe/Shopify 등 멱등키 베스트프랙티스, HTTP 재시도 패턴.

## 11) 보안(TLS, MTA-STS, 악성 첨부)

**결론**: **TLS 강제 + MTA-STS + AV/샌드박스**로 전송/콘텐츠 보안을 강화합니다.

**이론**: STARTTLS는 업그레이드형; MTA-STS는 정책으로 TLS를 강제하고 다운그레이드 방지.

**판단**: 최소 TLS1.2, 강한 CipherSuite, 링크 재쓰기/격리 영역에서 실행.

**의도**: 메일 특화 보안 레이어 인지.

**개선/한계**: 상호 TLS 미지원 MTA—옵션 협상 실패 시 정책에 따른 큐 지연/폴백.

**신입 액션**: 테스트 도메인에 MTA-STS 배포, TLS 스캐너로 점검 리포트 작성.

**근거**: RFC 3207(STARTTLS), MTA-STS 표준·보안 권고, OWASP TLS 가이드.

## 12) 용량·비용 관리(스토리지 수명주기)

**결론**: 핫/웜/콜드/아카이브 계층화와 중복제거(Content-Hash)로 비용을 줄입니다.

**이론**: 접근 빈도에 따른 스토리지 티어링과 수명주기 정책(IA/Glacier).

**판단**: 첨부는 hash-key로 중복 제거, 장기 미접근은 IA/Glacier로 이동, 삭제권(GDPR)은 키-객체 맵으로 추적.

**의도**: 비용-성능 트레이드오프 의사결정.

**개선/한계**: 복구 RTO 증가—장기 티어에 대한 사용자 기대치 공지 필요.

**신입 액션**: S3 수명주기 정책 PoC와 월간 비용 시뮬레이션.

**근거**: AWS S3 수명주기/Glacier 문서, 대규모 메일 아카이브 사례.
