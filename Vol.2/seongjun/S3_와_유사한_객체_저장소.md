    ## 1) 저장소 유형 비교 & 객체 저장소의 트레이드오프 — 면접자 답변
    
    ### 결론
    
    블록은 **최저 레벨 성능·지연**이 강점, 파일은 **POSIX 유사 인터페이스와 공유**가 강점, 객체는 **대규모 확장성·내구성·비용 효율**이 강점입니다. 본 문제의 전제처럼, 객체 저장소는 **성능을 일부 희생하고(상대적으로 높은 지연)** **내구성·가용성·저비용**을 극대화해 **쿨/콜드 데이터**에 최적화됩니다. S3 같은 상용 객체 저장소는 내구성(예: 11 9s)과 다중 AZ 내재화로 이 방향을 대표합니다. [Amazon Web Services, Inc.+2AWS Documentation+2](https://aws.amazon.com/compare/the-difference-between-block-file-object-storage/?utm_source=chatgpt.com)
    
    ### 근거와 선택 기준
    
    - **블록 저장소**: 데이터가 균등 블록으로 쪼개져 호스트가 파일시스템/DB를 직접 올립니다. 초저지연 트랜잭션 워크로드(DB, VM 부트 디스크)에 유리합니다. [Amazon Web Services, Inc.](https://aws.amazon.com/compare/the-difference-between-block-file-object-storage/?utm_source=chatgpt.com)
    - **파일 저장소**: 블록 위에 파일/디렉터리 추상화를 얹어 **공유와 단순 운영**이 강점입니다. 팀 공유 홈디렉터리, 컨텐츠 협업 등에 적합합니다. [Google Cloud+1](https://cloud.google.com/discover/object-vs-block-vs-file-storage?utm_source=chatgpt.com)
    - **객체 저장소**: **평면 네임스페이스 + 키/값 + REST API**로 대규모 비정형 데이터를 저비용으로 저장합니다. 강한 내구성·가용성, 다중 AZ/지역 중복을 기본 제공하는 서비스가 많습니다. (S3의 11 9s 내구성, 99.99% 가용성 지향 등) [AWS Documentation+2Amazon Web Services, Inc.+2](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DataDurability.html?utm_source=chatgpt.com)
    
    > 본 과제 요건(“성능 일부 희생, 쿨 데이터, REST API, 대규모/저비용”)은 전형적인 객체 저장소의 설계 철학과 일치합니다. IBM+1

    ### 실무 적용 예
    
    - **로그/백업/미디어**: 대용량 파일을 **멀티파트 업로드**로 병렬 전송 후 서버에서 조립 → 장거리 네트워크에서도 안정적으로 처리(부분 재전송 가능). 비용·내구성 관점에서 객체 저장소 선택. [AWS Documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html?utm_source=chatgpt.com)

    ### 꼬리질문 대응
    
    **꼬리1) “성능을 의도적으로 희생”의 의미와 정당화 워크로드?**
    
    의미: 블록/파일 대비 **높은 지연과 낮은 IOPS**를 감수하는 대신, **고내구성(다중 AZ 복제/소거코드), 무한에 가까운 확장성, GB·TB·PB 단위 저비용**을 얻습니다. 정당화되는 워크로드는 **백업/아카이브/로그/미디어 저장/데이터레이크 원본** 등 **읽기:쓰기 비율이 높고(Write once, read many), 즉시성 요구가 낮은** 경우입니다. (S3의 11 9s 내구성, 99.99% 가용성, 다중 AZ 저장 설계) [AWS Documentation+1](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DataDurability.html?utm_source=chatgpt.com)
    
    **꼬리2) 핫 트래픽 투입 시 병목?**
    
    주요 병목은 **네트워크 왕복 지연 + HTTP 오버헤드 + 객체 단위 접근 특성**입니다. 초당 소량·랜덤 I/O가 많은 트랜잭션형 워크로드(DB/메타데이터 업데이트 잦은 서비스)는 **블록/파일**이 더 적합합니다. 객체는 CDN/캐시를 두거나, 핫셋은 별도 계층(예: 파일/NAS)으로 분리해 완화합니다. [IBM](https://www.ibm.com/think/topics/object-vs-file-vs-block-storage?utm_source=chatgpt.com)
    
    **꼬리3) 파일 공유/NAS 요구 시 왜 파일 저장소?**
    
    파일 저장소는 **디렉터리/권한/파일잠금 등 익숙한 파일시스템语義**를 제공해 **사용자·팀 공유**에 적합합니다. 객체 저장소는 **평면 네임스페이스/최소 API**로 목록·권한 모델이 다르고, POSIX 호환이 아니라 마이그레이션 비용이 큽니다. 조직 내부 공유 드라이브, DCC(디지털 콘텐츠 협업) 같은 시나리오는 파일 저장소가 합리적입니다. [Google Cloud](https://cloud.google.com/discover/object-vs-block-vs-file-storage?utm_source=chatgpt.com)

## 2) API 서비스–메타데이터–데이터 노드 아키텍처

**Q2.** 로드밸런서–API 서비스–메타데이터 저장소–데이터 저장소(데이터 노드)의 역할을 요청 흐름 기준으로 설명해 보세요.

- 꼬리1) 데이터 라우팅 서비스와 배치 서비스의 역할을 분리하는 이유는 무엇이며, 분리하지 않았을 때 생길 결합 문제는 무엇인가요?
- 꼬리2) 데이터 노드가 주기적으로 전송하는 “박동 메시지(heartbeat)”에 포함되는 정보가 설계상 왜 필요한가요? (예: 드라이브 수, 사용량)
- 꼬리3) 초기 등록 시 데이터 노드에 내려주는 “가상 클러스터 지도”와 “사본 보관 위치” 정보가 장애 격리에 어떻게 기여하는지 설명해 보세요.
- 답변
    
    ### 메인 질문 답변
    
    “요청 처리는 **로드밸런서 → API 서비스 → 메타데이터/라우팅 → 데이터 노드** 순으로 갑니다.
    
    먼저 **API 서비스**가 인증·권한을 통과시킨 뒤 버킷/객체의 **메타데이터 유효성**(버킷 존재, 버전 정책, 네임 규칙 등)을 확인합니다. 이어서 **데이터 라우팅 서비스**가 **배치 서비스의 정책**과 **현재 클러스터 상태**(노드 용량·사용률·장애 도메인)를 입력으로 받아, 사본을 어느 **데이터 노드**들에 쓸지 결정합니다.
    
    쓰기 경로는 **객체 크기별로 최적화**합니다.
    
    - **소형 객체**는 각 노드의 **append-only 데이터 파일** 뒤에 붙이고(랜덤 I/O를 순차 I/O화),
    - **대형 객체**는 **멀티파트 업로드**로 병렬 수신한 뒤 서버에서 조립합니다.
    
    데이터 노드는 실제 바이트를 기록한 후, **데이터 파일 식별자 + 파일 내 오프셋 + 길이**를 산출합니다. 이 3가지가 객체의 물리 위치 인덱스이므로, API 서비스가 최종적으로 **메타데이터 저장소**(예: object_mapping 테이블)에 커밋하고 클라이언트에는 **UUID**를 응답합니다.
    
    이 구조의 의도는 **제어면(API·메타데이터)** 과 **데이터면(대용량 바이트 I/O)** 을 분리해서 독립 확장하고, 라우팅/배치로 **장애 도메인 분산**을 강제해 **내구성/가용성** 목표(다중 AZ 분산, 식스 나인 내구성)에 맞추는 것입니다.”

    ### 꼬리질문 1) 왜 “라우팅”과 “배치”를 분리했나요?
    
    “각자의 책임이 다릅니다.
    
    - **배치 서비스**는 ‘정책·토폴로지’를 가집니다. 예: **사본은 서로 다른 AZ/랙/호스트에** 분산, 노드 클래스별 가중치, 디스크 타입 혼합 금지 등 **규칙**을 정의하고 지속 관리합니다.
    - **라우팅 서비스**는 해당 **정책을 실행**하는 계층으로, ‘지금 이 순간’의 **실시간 상태**(하트비트로 수집된 용량·사용률·부하)를 고려해 **목적지 후보를 선택**합니다.
    
    이걸 섞으면 정책을 바꿀 때마다 데이터 경로 코드를 배포해야 하고, 핫스팟이 생겨도 **정책/가중치 조정**을 빠르게 반영하기 어렵습니다. 분리해두면 운영자는 정책만 교체·버전업해서 **무중단으로 배치 기준**을 바꿀 수 있고, 라우팅은 그대로 **실시간 최적 선택**에 집중합니다. 결과적으로 핫버킷/핫키가 생겨도 정책 가중치 조정만으로 빠르게 **트래픽 재분산**이 가능합니다.”

    ### 꼬리질문 2) 데이터 노드 하트비트에 무엇이 담기고 왜 필요하죠?
    
    “**하트비트**에는 최소 **(1) 부착 디스크 수, (2) 각 디스크 사용량/잔여 용량, (3) 노드별 저장된 데이터 양, (4) 최근 I/O 실패나 에러율** 같은 신호가 들어갑니다.
    
    이 정보는 두 가지에 직접 쓰입니다.
    
    1. **선제적 핫스팟 회피**: 라우팅이 잔여 용량이 적거나 에러율이 높은 노드는 우선순위에서 내리고, 여유 있는 노드로 **균형 분산**합니다.
    2. **내구성 유지(재복제 트리거)**: 하트비트 미수신/에러율 상승은 장애 신호이므로, 배치가 **사본 수 부족**을 감지하면 다른 실패 도메인으로 즉시 **재복제**를 시킵니다.
    
    핵심은 하트비트로 클러스터 ‘현주소’를 끊임없이 수집해, **정책(배치)** 과 **현실(라우팅)** 을 일치시키는 겁니다.”

    ### 꼬리질문 3) ‘가상 클러스터 지도’와 ‘사본 보관 위치’가 장애 격리에 어떻게 기여하나요?
    
    “**가상 클러스터 지도**는 클러스터의 **실패 도메인 계층**(호스트→랙→AZ 등)과 **선택 규칙**을 담은 ‘룰북’입니다. 데이터 노드는 등록 시 이 지도를 받아 ‘같은 랙/같은 AZ에 사본이 몰리지 않게’ 하는 **배치 규칙**을 공유합니다.
    
    그 결과 사본이 **물리적으로 분리**되어 저장되므로, 한 호스트나 한 랙, 심지어 한 AZ가 통째로 장애여도 **다른 도메인에 있는 사본**으로 서비스가 계속 가능하고, 백그라운드에서 **빠른 재복제**로 목표 사본 수를 회복합니다. 요건의 **식스 나인 내구성/포 나인 가용성**을 뒷받침하는 가장 직접적인 메커니즘입니다.”
    
    ---
    
    ### 한 줄 마무리
    
    “정리하면, **제어면과 데이터면 분리**, **정책(배치)과 실행(라우팅) 분리**, **하트비트 기반 실시간 상태 반영**, **가상 지도에 의한 실패 도메인 강제 분산**—이 네 축으로 **확장성·내구성·운영 단순성**을 동시에 달성합니다.”

## 3) 객체 저장/조회 경로 & 작은 객체 처리

**Q3.** “개선된 데이터 저장 흐름” 4단계를 따라, API 요청부터 object_mapping 업데이트까지의 쓰기 경로를 상세히 말해 보세요.

- 꼬리1) 모든 객체를 “개별 파일”로 저장하지 않고 “작은 객체를 큰 파일에 모아 Append”하는 방식을 채택하는 이유와, 그로 인한 운영 상 주의점은 무엇인가요? (예: inode 한계, 내부 단편화)
- 꼬리2) UUID로 객체를 찾기 위해 필요한 세 가지 메타정보(데이터 파일, 파일 내 오프셋, 크기)를 어디에 어떻게 보관할지, 그리고 왜 “읽기 성능 좋은 RDB”가 적합한지 근거를 대 보세요.
- 꼬리3) 다운로드 시 “버킷은 디렉터리 계층을 제공하지 않는다”는 제약을 어떻게 우회해 논리적 계층(접두어)을 제공하나요? 클라이언트/서버 어느 쪽에서 어떤 변환을 담당하나요?
- 답변
    
    “저는 개선된 쓰기 경로를 **네 단계**로 설명하겠습니다.
    
    **1)** API 서비스가 인증·권한을 통과시키고 버킷/키 유효성을 확인합니다. **2)** 데이터 라우팅이 배치 정책과 현재 클러스터 상태를 반영해 사본을 기록할 데이터 노드 집합을 고릅니다. **3)** 데이터 노드는 객체 크기에 따라 소형은 **append-only 데이터 파일** 뒤에 붙이고, 대형은 **멀티파트 업로드**로 병렬 수신 후 조립합니다. 이때 파일 식별자, **오프셋·길이, 체크섬**을 산출하고 디스크에 **fsync(또는 저널/WAL)** 로 내구성을 확보합니다. **4)** 마지막으로 API 서비스가 메타데이터 저장소의 `object_mapping`에 **{bucket, object, version, file_id, offset, length, checksum}** 를 트랜잭션으로 커밋하고, 클라이언트에는 **UUID**(또는 {bucket, object, version})를 응답합니다. 데이터→메타데이터 순서로 커밋하기 때문에 커밋 실패분은 고아 세그먼트로 표시되어 **GC**로 회수 가능합니다.”
    
    ---
    
    ### 꼬리질문 1) 왜 개별 파일 대신 ‘작은 객체 Append’인가? 운영 주의점은?
    
    “소형 객체를 개별 파일로 쓰면 **inode 고갈**과 **랜덤 I/O 시킹**이 급증합니다. 큰 파일에 **순차 append**하면 inode 사용을 줄이고 HDD에서도 효율이 좋습니다. 다만 운영 상 **내부 단편화**가 생기므로 주기적 **컴팩션/GC**가 필요하고, 데이터 파일은 **크기/시간 기준 롤오버**를 걸어 복구·압축 비용을 제한합니다. 또 append 성공 후 메타데이터 커밋이 실패한 건 **고아 플래그**로 표기해 백그라운드에서 수거하고, 저장 시 **체크섬**을 기록해 스크러빙으로 무결성을 재검증합니다.”
    
    ---
    
    ### 꼬리질문 2) UUID 조회에 필요한 메타정보 보관 방식과 RDB를 쓰는 이유?
    
    “UUID → 실제 바이트 범위를 바로 찾아가려면 **세 가지**가 필요합니다: **데이터 파일 식별자(file_id), 파일 내 오프셋(offset), 길이(length)**. 저는 이를 메타데이터 저장소의 `object_mapping` 테이블에 **단일 행**으로 저장하고, PK를 `{uuid}` 또는 `{bucket, object, version}`로 둡니다. 조회 패턴이 ‘키 한 건 → 행 한 건’ 형태의 **인덱스 룩업**이기 때문에 **읽기 지연이 낮은 RDB**가 적합하고, 트랜잭션 경계가 명확해 쓰기 커밋 일관성도 확보됩니다. 규모가 커지면 `{bucket_name+object_name}` 기반 **샤딩**과 **리드 레플리카**로 목록/조회 부하를 분산합니다.”
    
    ---
    
    ### 꼬리질문 3) 디렉터리 계층이 없는데, 접두어로 논리 계층을 어떻게 제공하나? 서버/클라이언트 역할은?
    
    “키 네이밍을 `photos/2025/09/img.png`처럼 **접두어(prefix)** 규칙으로 잡고, **서버**가 `prefix` 조건으로 필터링한 뒤 **구분자(`/`) 이후 토큰을 그룹화**해 ‘폴더처럼’ 보이게 가공해 반환합니다. **클라이언트**는 이 응답을 받아 디렉터리·파일 UI로 렌더링하면 됩니다. 대량 범위를 안전하게 처리하려고 서버는 **정렬 일관성(키 사전순)** 과 **페이지네이션 토큰**(샤드별 커서를 통합한 커서)을 사용하고, 요청당 **limit/스트리밍**으로 메모리 폭주와 타임아웃을 방지합니다.”

## 4) 내구성(Replication vs. 소거 코드) & 정확성 검증

**Q4.** “식스 나인 내구성”을 달성하기 위한 기본 전략(복제, 장애 도메인 분리)을 설명하고, 소거 코드 채택 시 얻는 이점과 지연 비용을 비교해 보세요.

- 꼬리1) AZ(가용 영역) 간 복제가 내구성에 기여하는 기전과, 동일 AZ 내 복제만 했을 때의 리스크를 구체적으로 말해 보세요.
- 꼬리2) 소거 코드에서 일부 노드가 손실되어도 복구 가능한 이유를 원리 수준에서 설명하고, “최대 4노드 장애 허용” 같은 파라미터가 의미하는 바를 해석해 보세요.
- 꼬리3) 체크섬(MD5/SHA1/HMAC 등)을 이용한 무결성 검증이 쓰기·복구·백그라운드 스크러빙 어디에 개입할 수 있는지, 각각의 트레이드오프를 말해 보세요.
- 답변
    
    ### 메인 질문) 내구성(복제 vs 소거 코드) & 정확성 검증 — 제 답변
    
    “저는 **장애 도메인 분산 + 저장 방식 선택**을 묶어 내구성을 달성합니다.
    
    우선 사본은 **서로 다른 실패 도메인(AZ/랙/호스트)** 에 강제로 분산시켜 단일 도메인 장애 영향권을 끊습니다. 저장 방식은 워크로드에 따라 **복제(Replication)** 와 **소거 코드(Erasure Coding)** 를 선택·혼용합니다.
    
    - **복제**는 쓰기 경로가 단순하고 지연이 낮아 핫 패스(메타데이터, 작은 객체)에서 유리합니다. 다만 저장 오버헤드가 큽니다.
    - **소거 코드는** 데이터를 조각+패리티로 나누어 분산 저장해 **저장 비용을 낮추면서 내구성**을 높입니다. 이 설계에서는 **동시에 최대 4노드 장애**도 복구가 가능하도록 파라미터를 잡을 수 있지만, 읽기/복구 시 **여러 노드(최대 8개 등)에서 병렬로 모아야 하므로 지연이 증가**합니다.
    
    정확성은 **체크섬 기반**으로 보증합니다. 쓰기 시 객체의 체크섬을 생성해 메타데이터에 함께 커밋하고, 읽기/복구/백그라운드 스크러빙에서 다시 계산해 **불일치 시 손상으로 판정**합니다. 손상이 발견되면 남은 사본(복제) 혹은 **데이터+패리티(소거 코드)** 로 **원본 복구 후 재복제**해 목표 사본 수를 회복합니다. 이 조합으로 요구된 **식스 나인 내구성, 포 나인 가용성** 목표를 충족시키는 게 제 설계의 핵심입니다.”
    
    ---
    
    ### 꼬리질문 1) AZ 간 복제가 왜 중요한가요? 동일 AZ 내 복제의 리스크는?
    
    “복제의 목적은 ‘**공동 실패를 피하는 것**’입니다. 동일 AZ 내부 복제만 하면 정전·코어 네트워크·냉각·화재 같은 **공통 원인 장애**에서 모든 사본을 동시에 잃을 수 있습니다. 반대로 **AZ 분산**을 강제하면 하나의 AZ가 불능이어도 **다른 AZ 사본으로 즉시 제공**하고, 백그라운드에서 **재복제**로 목표 사본 수를 회복해 **내구성과 가용성**을 동시에 보장할 수 있습니다.”
    
    ---
    
    ### 꼬리질문 2) 소거 코드로 ‘최대 4노드 장애 허용’이 가능하다는 말의 의미는?
    
    “소거 코드는 *(데이터 k + 패리티 m)* 스킴으로 운영합니다. 여기서 **m이 허용 가능한 동시 장애 수**를 의미합니다. ‘최대 4노드 장애 허용’은 **패리티가 최소 4개**여서, 동일 객체에 대한 조각 중 **최대 4개가 동시에 유실되어도 남은 데이터+패리티로 원본을 복구**할 수 있다는 뜻입니다. 단, 그 대가로 **복구 계산/네트워크 수집 비용과 읽기 지연**이 늘어납니다. 그래서 저는 **콜드/쿨 데이터**에 소거 코드를 주로 적용하고, **핫 경로**는 복제를 우선합니다.”
    
    ---
    
    ### 꼬리질문 3) 체크섬을 어디에, 언제 쓰나? 쓰기·복구·스크러빙 각각에서요.
    
    “체크섬은 **쓰기, 제공, 유지보수** 전 단계에 개입합니다.
    
    - **쓰기**: 저장 직후 **체크섬을 계산**해 메타데이터에 함께 기록합니다(객체의 무결성 스냅샷).
    - **제공/복구**: 다운로드 시 **다시 계산해 비교**하고 불일치면 ‘손상’으로 판정, 복제면 **다른 사본 재시도**, 소거 코드면 **남은 조각+패리티로 재조립** 후 정합 체크, 필요 시 **재복제**까지 진행합니다.
    - **백그라운드 스크러빙**: 주기적으로 저장 조각을 샘플링/전수 검사해 **무음 비트로트**를 조기에 탐지하고, 발견 즉시 **복구→정합 확인→메타데이터 업데이트** 순으로 표준 워크플로를 밟습니다.
    
    이 흐름으로 **정확성 검증이 상시 자동화**되고, 손상·유실을 내구성 손실로 번지기 전에 차단할 수 있습니다.”

## 5) 메타데이터 스키마/샤딩 & 버킷 목록/버전/멀티파트/GC

**Q5.** bucket/object 스키마를 전제로, “버킷 내 객체 목록”과 “버전 관리”를 어떻게 구현할지(단일 DB vs. 분산 DB) 접근 방식을 비교해 보세요.

- 꼬리1) object 메타데이터 샤딩 키를 (a) bucket_id, (b) object_id, (c) bucket_name+object_name 중 무엇으로 둘 때 어떤 질의 패턴에서 이점/한계가 생기나요?
- 꼬리2) 대용량 파일 업로드에서 멀티파트 업로드를 도입할 때 서버 측 조립 이후 “조각(파트) 정리”는 어떤 전략(GC)이 필요하며, “지연 삭제·고아 데이터·훼손 데이터”를 각각 어떻게 수거하나요?
- 꼬리3) “읽기 부하 분산을 위해 DB 리드 리플리카”를 둘 때, 접두어 기반 리스트 요청이 여러 샤드/사본에 걸쳐 있을 경우 커서/오프셋을 어떻게 추적·통합해 일관된 페이지네이션을 보장하나요?
- 답변
    
    ### 메인 질문) 단일 DB vs. 분산 DB에서 “버킷 내 객체 목록”과 “버전 관리”를 어떻게 구현할 건가요?
    
    “핵심은 **URI 기반 접근( bucket_name + object_name )**을 일관되게 잡고, **목록은 접두어(prefix) + 구분자(`/`) 그룹화**, **버전은 최신 우선**입니다.
    
    - **단일 DB**: `bucket_name + object_name` 인덱스로 **prefix 필터**를 빠르게 처리합니다. ‘디렉터리처럼 보이게’는 서버가 `/` 기준으로 **토큰을 그룹화**해서 반환합니다. 버전 관리는 같은 `(bucket, object)` 묶음에서 **object_version DESC** 정렬로 **최신을 기본**으로 주고, 옵션이 있으면 **모든 버전**을 페이지네이션으로 스트리밍합니다.
    - **분산 DB(샤딩)**: 샤드키를 **(bucket_name + object_name)** 로 두면 **URI 질의와 일치**해서 핫스팟을 피하고, prefix 목록은 **샤드별 커서**를 유지한 뒤 서버에서 **병합 정렬**로 전역 순서를 맞춥니다. 클라이언트는 전역 **continuation token** 하나만 봅니다.
    - 공통 운영: 리스트는 **사전순(바이트 정렬)** 을 기준으로 하고, **limit + 지속 커서**로 일관된 페이지네이션을 보장합니다. 버전의 기본 응답은 “최신만”, 필요 시 `versions=true`로 과거 버전을 포함해 줍니다.”
    
    ---
    
    ### 꼬리질문 1) 샤딩 키 선택 — (a) bucket_id, (b) object_id, (c) bucket_name+object_name
    
    “**(c)** 를 우선합니다.
    
    - **(a) bucket_id**: 버킷 단위로는 균등하지만, **특정 버킷이 핫**해지면 샤드 핫스팟을 피하기 어렵습니다(대형 단일 버킷 워크로드에서 취약).
    - **(b) object_id(난수)**: 분산은 잘 되지만, **URI 기반 질의(접두어, 폴더 흉내)** 가 비효율적입니다(전 샤드 브로드캐스트 증가).
    - **(c) bucket_name+object_name**: 실제 질의 패턴과 **정합**합니다. **prefix 스캔·사전순 정렬·의사 디렉터리**가 자연스럽게 되고, 키 분포도 비교적 균등합니다(네이밍 규칙만 관리하면 핫키 완화도 수월).”
    
    ---
    
    ### 꼬리질문 2) 멀티파트 업로드 후 “조각(파트)” 정리는 어떻게 하나요? (GC 관점: 지연 삭제/고아/훼손)
    
    “원칙은 **조립 성공을 커밋 시점**으로 봅니다.
    
    1. **지연 삭제**: 조립 완료 후 최종 객체가 노출되면, 파트는 **참조 해제만 먼저** 하고 실제 공간 회수는 **백그라운드 GC**가 합니다(피크 시간 회피).
    2. **고아 데이터**: 업로드 중단·클라이언트 실패 등으로 **최종 커밋이 없던 파트**는 TTL이 지난 뒤 **고아 스캔**으로 일괄 수거합니다(업로드 ID/상태로 판별).
    3. **훼손 데이터**: 저장 시 기록한 **체크섬**을 스크러빙에서 재검증하고, 불일치 시 **사본/소거 코드**로 즉시 복구 후, 손상 조각은 교체합니다.
    4. **스로틀링**: 대량 삭제나 파트 정리 시 **IO·네트워크 기준 스로틀**과 **시간 창(오프피크 슬롯)** 을 둬서 사용자 경로 지연 상승을 막습니다.”
    
    ---
    
    ### 꼬리질문 3) 리드 레플리카 사용 시, 접두어 목록의 **커서/오프셋 일관성**은 어떻게 보장하나요?
    
    “두 가지를 지킵니다.
    
    - **커서 설계**: 커서는 단순 오프셋이 아니라 **(마지막 키, 샤드별 위치)** 정보를 담은 **논리 커서**입니다. 다음 호출에서 서버가 각 샤드 **로컬 커서**를 재개해 **병합 정렬**을 이어갑니다(중복·누락 방지).
    - **일관성 전략**: 강한 일관성이 필요한 짧은 구간(갓 업로드된 범위)은 **일시적으로 프라이머리로 라우팅**하거나, **버킷 단위 지연 읽기(소폭의 read-your-writes 보장)** 정책을 둡니다. 일반 목록은 **최종적 일관성**으로 처리하되, 정렬·커서만 엄격히 유지하면 사용자 체감은 안정적입니다.”
    
    ---
    
    ### 한 줄 마무리
    
    “정리하면, **(bucket_name+object_name) 중심의 URI 키 설계**로 단일·분산 모두에서 **prefix·사전순·의사 디렉터리**를 자연스럽게 지원하고, 멀티파트는 **커밋 시점 확정 + 백그라운드 GC**로 공간을 회수합니다. 리드 레플리카를 써도 **논리 커서 + 병합 정렬**로 목록의 **일관된 페이지네이션**을 보장합니다.”
